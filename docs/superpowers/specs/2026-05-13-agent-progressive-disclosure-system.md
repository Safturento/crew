# Agent-context progressive disclosure system

## Context

The repo's agent-facing documentation has grown unevenly. Root `CLAUDE.md` is 61 lines but mixes architecture rules, dev setup, docker isolation, and Bruno conventions. `docs/plans/architecture.md` (258 lines), `docs/plans/design-system.md` (441 lines), `docs/plans/project-resolution.md`, and `docs/plans/sandbox-limitations.md` carry overlapping content that's partly current rules and partly historical narrative. No per-package documentation exists. The four packages (`cli`, `daemon`, `dashboard`, `shared`) have meaningfully different concerns, but agents working in any one of them load the same monolithic context.

Two failure modes drive this spec:

1. **Context bloat** — auto-loaded docs consume context budget before the agent does any work. Stale phrasing in those docs further confuses model reasoning.
2. **Stale or contradictory guidance** — docs disagree with each other or with the code. Agents pick the wrong source of truth and act on it.

The solution is a two-tier progressive-disclosure system based on the cross-tool `AGENTS.md` convention (now read natively by Claude Code, Codex CLI, Cursor, and most other AI coding tools as of early 2026), with a repo-scoped topic library at `.agents/`, machine-checkable freshness signals, and a parity enforcement layer that prevents code edits from outpacing the docs that govern them.

## Goals

- A root `AGENTS.md` under 60 lines that orients agents and indexes everything else.
- Per-package `AGENTS.md` files that lazy-load only when the agent touches that package, narrowing context to package-local rules.
- A topic library at `.agents/` whose files load on demand when referenced.
- A self-describing meta-doc (`.agents/README.md`) that captures how the system works, how to extend it, and how to keep it parity'd with code.
- Frontmatter-based staleness signals (`last_updated`) and code-coverage declarations (`covers:`) that enable both human and machine staleness/parity checks.
- A soft hook on commit/PR creation that warns when code changes touch a doc's `covers:` scope without updating the doc.
- Layer-1 metrics derivable from existing transcripts that measure whether the system is working.
- Forward compatibility with a future hybrid trigger system (auto-injection via prompt-builder).

## Non-goals

- Building the hybrid trigger system (auto-injection via prompt builder) in this spec — only the frontmatter affordances for it.
- Custom domain-specialized subagents (one-per-package). Out of scope; tracked as a separate brainstorm.
- A Layer-2 regression suite or Layer-3 A/B comparison harness. Filed as follow-ups once Layer-1 lands.
- Auto-generation of `.agents/` indexes. The manual index forces editorial discipline.

## System overview

Three tiers of context, ordered by load priority:

1. **Always-loaded.** Root `AGENTS.md`. Lean (<60 lines). Index of the system.
2. **Lazy-loaded by path traversal.** Per-package `AGENTS.md` at `packages/<pkg>/AGENTS.md`. Claude Code (and the cross-tool ecosystem) loads these automatically when the agent reads or writes a file in that directory. ~30–50 lines each.
3. **Discovery-on-demand.** Topic docs at `.agents/<topic>.md`. Loaded only when an AGENTS.md index entry directs the agent to them, or — in the future — when a frontmatter trigger fires.

The discovery model is **indexed by AGENTS.md** (Option 1 in the brainstorm), with frontmatter affordances reserved for a future hybrid trigger system (Option 3) applied selectively to docs where missing the convention is catastrophic.

## Frontmatter convention

Every `.agents/<topic>.md` declares:

```yaml
---
name: architecture
description: 4-package layering rules + dependency direction
last_updated: 2026-05-13
covers:
  - 'packages/*/src/**/*.ts'
  - 'package.json'
---
```

| Field          | Required | Purpose                                                                       |
| -------------- | -------- | ----------------------------------------------------------------------------- |
| `name`         | yes      | kebab-case slug; matches filename without `.md`                               |
| `description`  | yes      | One-line summary; root `AGENTS.md` index cites this verbatim                  |
| `last_updated` | yes      | ISO date; bumped whenever the body materially changes                         |
| `covers`       | yes      | Path globs the doc claims to govern; consumed by parity hook + future audits  |
| `globs`        | reserved | AGENTS.md community trigger field; activates when hybrid trigger system lands |
| `alwaysApply`  | reserved | Same                                                                          |

Per-package `AGENTS.md` frontmatter is lighter (no `covers:` — path-scoped by location):

```yaml
---
description: Patterns and rules for the `crew-cli` package
last_updated: 2026-05-13
---
```

Root `AGENTS.md` has no frontmatter.

A validator script (`scripts/validate-agents-frontmatter.ts`) wired into `npm run lint` asserts:

- Every `.agents/*.md` has all required frontmatter fields
- Every `covers:` glob is a valid micromatch pattern
- Every `name:` matches its filename

## Per-package AGENTS.md template

Each `packages/<pkg>/AGENTS.md` follows a consistent shape, ~30–50 lines:

```markdown
---
description: Patterns and rules for the `<pkg>` package
last_updated: YYYY-MM-DD
---

# <pkg>

[1-2 sentence framing of what this package is for]

## Rules specific to this package

- [package-local rules too narrow for .agents/architecture.md but too important to bury]

## When you need it

| Doing       | Read                 |
| ----------- | -------------------- |
| <task type> | `.agents/<topic>.md` |
| <task type> | <skill or topic doc> |

## Common gotchas

- [package-specific tripwires]
```

Per-package content sketch:

- **`cli/AGENTS.md`** — "thin wrapper" rule, lib-subdir ownership, no business logic, where dispatch flow lives.
- **`daemon/AGENTS.md`** — Fastify+Zod+Kysely+Awilix layering (defers to `reaching-for-backend-patterns` skill), routes-services-migrations layout, "no disk reads for things the CLI can pass" rule.
- **`dashboard/AGENTS.md`** — React+Vite+Tailwind, `components/ui` vs `components/<feature>` split, "no business logic; view over the daemon's API" rule, defers to `reaching-for-frontend-libraries` + `visual-fidelity-check` skills.
- **`shared/AGENTS.md`** — the leaf rule: no imports from cli/daemon/dashboard; types + small utilities only.

The "When you need it" table is the **package-scoped index** into `.agents/`. Root `AGENTS.md` has the global index; package `AGENTS.md` narrows it to what's likely while working in that package.

## Meta-doc structure (`.agents/README.md`)

Self-describing. Sections in order:

1. **What this is.** Two-tier progressive disclosure for agent context. AGENTS.md files auto-load; `.agents/<topic>.md` loads on demand. User-level skills (`~/.claude/skills/`) and conventions (`~/.claude/conventions/`) are orthogonal — they teach _how_; `.agents/` captures _what this repo is_.
2. **Discovery model.** Today: indexed by AGENTS.md. Future: opt-in frontmatter triggers.
3. **Frontmatter spec.** The field table from this spec, with reserved fields noted.
4. **When to add a topic file.** Three criteria (all must be true):
   1. Repo-specific (not universal — universal belongs in `~/.claude/conventions/`).
   2. Referenced by ≥2 places (one AGENTS.md or one PR-review cycle isn't enough; that's inline-doc material).
   3. Has a clear `covers:` scope (you can name path globs).
5. **When to split a topic into a folder.** Cross ~200 lines AND has natural subdivisions, OR one section is consistently the only part agents need.
6. **Parity rule — the load-bearing one.** If you edit code matching a `.agents/<topic>.md`'s `covers:` glob, audit that doc in the same PR. Update or confirm-still-current. Enforced by self-audit at completion + soft hook on commit/PR.
7. **Staleness signals.** Freshness gauge thresholds:
   - <30 days → trust.
   - 30–90 days → trust but verify load-bearing claims if they affect your work.
   - > 90 days → don't trust without checking; bump the date in your PR if confirmed correct.
8. **Trigger system (future).** Hybrid Option-3 deferred. When it lands, opted-in docs gain `globs:` + `alwaysApply:` frontmatter; the `crew run` prompt builder walks `.agents/` triggers and auto-injects matched docs.
9. **Naming conventions.** kebab-case files, no dates in filenames, filename matches frontmatter `name`.
10. **What does NOT belong in `.agents/`.** Explicit taxonomy with each kind of doc routed to its home:

    | Content                                                  | Home                                    |
    | -------------------------------------------------------- | --------------------------------------- |
    | Per-ticket work log                                      | `docs/tickets/<KEY>.md`                 |
    | Design specs (point-in-time, from brainstorming)         | `docs/superpowers/specs/`               |
    | Implementation plans (point-in-time, from writing-plans) | `docs/superpowers/plans/`               |
    | Long-form architecture/design rationale                  | `docs/rationale/`                       |
    | Mumen-tier scoping                                       | `docs/mumen/`                           |
    | Project followups                                        | `docs/followups.md`                     |
    | Universal coding/git/Node conventions                    | `~/.claude/conventions/`                |
    | "How to do X" capability injection                       | user-level skills (`~/.claude/skills/`) |
    | Per-conversation notes / todos / in-flight state         | not committed                           |

    `.agents/` is for _repo-specific, durable, agent-actionable rules_. If a doc isn't all three, it lives somewhere else above.

    **Pointers vs content.** The rule above is about _content_ sitting in `.agents/`, not about _cross-references_. A `.agents/<topic>.md` MAY (and often SHOULD) include a brief footer pointer like `See docs/rationale/<topic>.md for the why` or `See user-level skill <name> for how`. Pointers improve discoverability without bringing narrative into the agent-actionable layer. Aim for one or two short lines; if a topic doc needs a paragraph of context from elsewhere, that's a sign the content classification was wrong.

11. **Index of current topic docs.** Manually maintained table. Same list cited from root `AGENTS.md`.

## Discovery model

Root `AGENTS.md` contains a top-level index:

```markdown
## When you need it

- Editing daemon services/routes → `.agents/architecture.md`, package `AGENTS.md`
- Adding a Bruno endpoint → `.agents/testing.md`
- Sandbox/host-network behavior → `.agents/local-dev.md`, `.agents/security.md`
- Writing a new CLI subcommand → `.agents/architecture.md`, `packages/cli/AGENTS.md`
- Touching dispatch flow → `.agents/dispatch.md`
- Updating crew's Figma DS → `.agents/design-system.md`
- Running verification commands → `.agents/commands.md`
```

Each per-package `AGENTS.md` carries a narrower index focused on tasks the agent is likely to do _in that package_. Lazy-loading + path traversal means a daemon-only edit never loads dashboard or cli AGENTS.md.

## Parity enforcement

Two checkpoints, same `covers:` frontmatter underneath:

**Self-audit at completion.** The `superpowers:verification-before-completion` user-level skill is extended to scan `.agents/` for `covers:` overlap before any "I'm done" claim. Agent reviews each matched doc, updates if needed, bumps `last_updated`.

**Soft hook on commit/PR.** A PreToolUse hook (sibling to `visual-fidelity-pr-gate`) fires on git commit / PR create. Walks the diff. For each `.agents/<topic>.md` whose `covers:` glob overlaps a changed path, checks whether the doc was touched in the same commit or has a `last_updated` ≥ commit date. Warns with the doc list; agent can override with a reason. Not blocking.

Both rely on the same frontmatter; the soft hook is the safety net for when the self-audit was skipped or rushed.

## Verification metrics (Layer-1)

Four metrics, all derivable from data already captured.

| #   | Metric                          | Question                                                                                    | Derivation                                                                                                                              | Target                    |
| --- | ------------------------------- | ------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------- | ------------------------- |
| 1   | **Doc-load coverage**           | Did the agent load the right topic docs?                                                    | Transcript Read calls to `.agents/**/*.md` ∩ docs whose `covers:` overlap the PR diff. coverage = \|loaded ∩ expected\| / \|expected\|. | ≥ 80%                     |
| 2   | **Cleanliness-check pass rate** | Did the agent run lint/typecheck/test:run/bruno:smoke/visual-fidelity before claiming done? | Bash tool calls between last edit and commit matched against `.agents/commands.md`.                                                     | ≥ 95%                     |
| 3   | **Context size at PR-claim**    | Is progressive disclosure keeping context lean?                                             | `usage.input_tokens` of the assistant message immediately before commit/PR creation.                                                    | Trending down vs baseline |
| 4   | **Doc-parity violations**       | When agents change covered code, do they update the doc?                                    | PR diff ∩ each `.agents/<topic>.md` `covers:` glob — doc must be touched in same PR or have `last_updated` ≥ commit date.               | ≤ 5%                      |

**Scope.** Metrics 1, 2, 4 are meaningful only for `crew run` dispatches (clean ticket scope). Metric 3 works for both interactive and dispatched but baselining is only easy for dispatches.

**Baseline capture (one-time, before deployment).** A throwaway script runs all four metrics against the last 20 `crew run` dispatches and stores rows with `baseline=true`. Without a baseline the question "did `.agents/` help" can't be answered. Hard ordering: this runs before Phase 2 lands.

**Garbage-in-garbage-out caveat.** Metrics depend on `covers:` globs being well-authored. A doc with `covers: ["**"]` makes Metric 1 trivially 100%. A doc with no `covers:` makes it un-measurable. The meta-doc parity rule + frontmatter validator catch the worst cases.

**Implementation surface.**

- `packages/shared/src/transcripts/` — extend parser to extract Bash command names + Read paths.
- `packages/daemon/src/services/` — new `MetricsService` derives the four metrics from ingested events.
- Schema: extend `runs` table with metric columns + a `baseline` boolean (migration).
- `packages/dashboard/src/routes/` — agent detail gets a Metrics tab; landing gets an aggregate trend widget.

Implementation lives in the metrics-pipeline ticket; this spec defines what to measure and where it surfaces.

## Migration plan

**Epic — Agent-context progressive disclosure system** (CREW-?).

### Phase 1 — Foundation (one ticket, blocking)

Single ticket. Lays down the system so subsequent work has something to slot into.

1. Create `.agents/README.md` (meta-doc) with the structure above.
2. Create `docs/rationale/` (empty initially).
3. Rename root `CLAUDE.md` → `AGENTS.md`. Add the topic index pointing at empty `.agents/<topic>.md` placeholders. **Keep the existing verbose content sections in place for now** — they're the source material that Phase 2 tickets pull from. Root `AGENTS.md` is temporarily not yet "lean"; that state is reached at the end of Phase 2 once all content has migrated and the inline sections can be removed.
4. Create stub `packages/<pkg>/AGENTS.md` files with the per-package template — frontmatter + empty "When you need it" table, ready to fill in.
5. Add the validator script (`scripts/validate-agents-frontmatter.ts`). Wire into `npm run lint`.
6. Sweep inbound references — replace "see CLAUDE.md" with "see AGENTS.md" anywhere in the codebase, in user-level CLAUDE.md (handled manually per the "don't ticket user-level work" rule), and in existing skill descriptions that mention this repo.
7. **Baseline capture (Phase 4a) folded in as the final step:** throwaway script runs the four metrics against the last 20 transcripts and stores `baseline=true` rows.

**Done when:** A fresh `crew run` against any ticket auto-loads root `AGENTS.md` (with original content intact + new index pointing at empty placeholders) + the relevant package `AGENTS.md`. Baseline rows exist in the daemon DB.

**Final cleanup at end of Phase 2:** once all topic docs are filled in and the inline content in root `AGENTS.md` has migrated, the inline sections are removed in a small follow-up commit. Root `AGENTS.md` reaches its final "lean index" state at that moment, not at the end of Phase 1.

**Content audit step (required for every Phase 2 ticket).** Before deleting a source doc, walk it section-by-section and classify each section as:

1. **Agent-actionable** → folded into the topic file (or per-package `AGENTS.md` if more local).
2. **Design rationale / historical narrative** → moved to `docs/rationale/<topic>.md`.
3. **Stale / superseded** → noted in the PR description with a one-line "removed because: …" so the deletion is recoverable in review.

The source file is only deleted when bucket (1) is consolidated and bucket (2) has a new home. The PR description doubles as the audit trail.

Each PR also fills in the matching entries in root `AGENTS.md`'s index and the relevant per-package `AGENTS.md`'s "When you need it" table.

`docs/plans/` is removed at the end of Phase 2 once empty.

## Out of scope / future work

- **Hybrid trigger system (Option 3).** Frontmatter affordances (`globs:`, `alwaysApply:`) are reserved in the schema. Activation deferred to a separate follow-up.
- **Custom domain-specialized subagents** (one-per-package). Out of scope; separate brainstorm.
- **Task-specialized subagents** (`docs-parity-audit`, `verification`, `dispatch-orchestrator`). Out of scope; the `covers:` frontmatter pre-paves the road for them.
- **Layer-2 regression suite** (re-running historical-failure tickets through the new system to measure prevention). Follow-up after Layer-1 lands.
- **Layer-3 A/B comparison harness.** Only justified if Layers 1+2 prove inconclusive.
- **Auto-generated `.agents/` indexes.** The manual index forces editorial discipline.

## Open questions

- **How aggressively do we backfill `last_updated` on existing skill descriptions that reference this repo?** User-level work, handled in-conversation; deferred to the manual-task slot.
- **When does the hybrid trigger system earn activation?** When at least one Layer-1 metric (likely Metric 1 — doc-load coverage) underperforms target despite well-authored `covers:` globs. Don't activate preemptively.
