# Figma snapshot as a committed artifact — design

**Date:** 2026-05-17
**Status:** Draft for review
**Branch:** `docs/figma-snapshot-committed-artifact`

## Context

`crew figma-snapshot` produces the data the `visual-fidelity-check` skill compares rendered UI
against — per-node `raw` REST data plus a Plugin-API `enrichment` tier (`componentProperties`,
`boundVariables`, `componentInstances`). Today it runs **pre-dispatch, on every `crew run`** of a
`[visual_fidelity]` project.

Two problems with that model surfaced while debugging CREW-152:

1. **The enrichment pass has never worked.** It spawns a headless `claude -p` subprocess to
   drive the Figma MCP; that subprocess can't reach the MCP (CREW-172 fixed the missing
   `--dangerously-skip-permissions`, but the run still produces zero enrichment — the headless
   subprocess is the wrong host for the Plugin API). Every `crew run` has silently shipped
   REST-only snapshots.
2. **Per-dispatch regeneration is waste.** The Figma file does not change between two unrelated
   `crew run`s. Regenerating the snapshot every dispatch re-does identical work — and it is
   exactly where the breakage lives.

The Figma Plugin API *does* work reliably — interactively, via the `figma` plugin MCP
(`use_figma`). It only fails in the headless subprocess. So the fix is to stop generating the
snapshot per-dispatch and instead make it a **committed artifact**, regenerated by an
interactive Claude session (where the MCP works) whenever the Figma design changes.

This was chosen over two alternatives: a direct Figma-MCP client in crew (real new
infrastructure for an occasionally-run command) and a fully-interactive regeneration with no
crew code (makes Claude hand-produce structured JSON + binary PNGs every time). See the
2026-05-17 brainstorm.

## The model

- The figma snapshot is a **committed file tree** in the crew repo.
- `crew run` does nothing Figma-related. The dispatched agent reads the committed snapshot at
  `snapshot_path` exactly as it reads a generated one today — the agent/skill side is unchanged.
- The snapshot is **regenerated by an interactive Claude session**, triggered when the Crew
  Figma design changes, before that design feeds into code implementation.

## Changes

### 1. Remove per-dispatch generation

Delete:

- `packages/cli/src/lib/run/figma-snapshot-step.ts` (`runPreDispatchFigmaSnapshot`) + its test.
- The pre-dispatch snapshot block in `packages/cli/src/commands/run.ts` (the
  `if (config.visual_fidelity) { … runPreDispatchFigmaSnapshot … }` block).
- The `export * from './figma-snapshot-step.js'` line in `packages/cli/src/lib/run/index.ts`.
- `packages/cli/src/lib/figma-snapshot/plugin-api-enrichment.ts` + its test — the broken
  headless-subprocess enrichment.
- `buildEnrichmentPrompt` in `enrichment-prompt.ts` + its test (the `claude -p` prompt
  machinery). **The `ENRICHMENT_SCRIPT` constant is kept** — relocated, see §3.

CREW-172's `lib/claude/spawn.ts` refactor (`CLAUDE_PERMISSION_FLAG`, `claudeSpawnEnv()`)
**survives** — `spawnClaudeResume`/`spawnClaudeFresh` still use it. Only the figma-snapshot
subprocess is removed.

### 2. `crew figma-snapshot` — REST export only, plus `--check`

`runFigmaSnapshot` keeps the REST export (`emitSnapshot` — file fetch, batched `/images` per
CREW-171, `index.json`, per-node `raw` JSON, PNGs). It drops the `enrichSnapshotWithPluginApi`
call. It is now a manually-invoked command, not a pre-dispatch hook.

At export time it records the Figma file's `version` (returned by the REST file response) into
the snapshot — written to `<snapshot_path>/index.json` as a top-level field (e.g.
`figmaFileVersion`). This is the anchor for staleness detection.

New flag **`crew figma-snapshot --check`**: fetches only the live Figma file metadata (a cheap
metadata request — *not* the render-prone `/images`), compares its `version` to the committed
snapshot's recorded `figmaFileVersion`, and reports `fresh` or `stale` without regenerating.
Exit non-zero on stale so it is scriptable.

### 3. The regeneration skill

A new skill **`figma-snapshot-refresh`** at `.claude/skills/figma-snapshot-refresh/`:

- `SKILL.md` — the procedure (also human-readable: a person can follow it or just invoke the
  skill).
- `enrichment-script.js` — the relocated `ENRICHMENT_SCRIPT` (the Plugin-API JS), a skill
  asset the procedure feeds to `use_figma`.

It is **not** added to `CREW_OWNED_SKILLS` — dispatched coding agents must not regenerate
snapshots; only interactive design sessions do. Living in `.claude/skills/` makes it
discoverable in interactive crew-repo sessions; staying off `CREW_OWNED_SKILLS` keeps it out of
dispatch injection.

**Procedure:**

1. **Freshness check.** Run `crew figma-snapshot --check`. If `fresh`, stop — the snapshot is
   already current; regeneration is a no-op. (This makes triggering the skill liberally cheap.)
2. **REST export.** Run `crew figma-snapshot` — lands `raw` JSON + `index.json` + PNGs at
   `.crew/figma-snapshot/`.
3. **Enrich.** Read the node IDs from `index.json`; call `mcp__plugin_figma_figma__use_figma`
   with `enrichment-script.js` (per the figma MCP's requirement, load `figma-use` first).
4. **Merge.** Write each returned `enrichment` object into its per-node JSON file.
5. **Verify (fail-closed).** Confirm every node JSON has a populated `enrichment` field with
   `componentInstances`. If `use_figma` errored or enrichment is empty, **stop — do not commit
   a REST-only snapshot.** Surface the failure.
6. **Commit** the snapshot tree.

### 4. The design-flow trigger

The skill must fire at the design→code handoff, not only on explicit human invocation.

- The skill's `description` triggers on: a Crew Figma design change made this session
  (`use_figma` writes, `figma-generate-design` / DS component or token work) and wrapping up
  toward code implementation.
- Because a `description` alone does not reliably self-trigger (crew's established gate-skill
  finding), the trigger is **reinforced in `.agents/design-system.md`** — the topic doc already
  loaded whenever someone touches the Crew Figma DS or `.figma.tsx`. It gains an explicit rule:
  *after any Crew DS design change, run `figma-snapshot-refresh` before the design feeds into
  code implementation.*

This makes `figma-snapshot-refresh` the producer-side gate (*after design, before code*),
paired with `visual-fidelity-check` as the consumer-side gate (*after code*).

### 5. Committed location & contents

- **Un-gitignore `.crew/figma-snapshot/`.** Add a negated-pattern exception to `.gitignore`,
  mirroring the existing `.claude/skills/` precedent (`.crew/` stays ignored otherwise). This
  keeps `snapshot_path`'s default — the agent already looks there.
- Commit the whole tree: `index.json`, per-node JSON, **and** the PNGs. The PNGs are a few MB,
  change only when the design changes, and `visual-fidelity-check` Step 5.5 cross-references
  them. Binary churn on an occasional-change artifact is acceptable.

### 6. Config

Remove `skip_snapshot` from `visualFidelitySchema` (`packages/shared/src/config/schema.ts`) —
with per-dispatch generation gone, there is nothing to skip. `figma_file_key`, `figma_pages`,
`snapshot_path`, `component_dir`, `code_connect_glob`, `dashboard_url` are unchanged.

### 7. Docs

- `.agents/dispatch.md` — remove the per-dispatch figma-snapshot step from the dispatch flow
  description; the snapshot is no longer a dispatch concern.
- `.agents/design-system.md` — add the trigger rule (§4).
- `docs/visual-fidelity-setup.md` — update: the snapshot is committed, not per-dispatch; how to
  regenerate (point at the skill); `--check` for staleness.

## Error handling

- **Regeneration fail-closed.** If `use_figma` errors or enrichment comes back empty, the skill
  stops at step 5 and does not commit. A committed snapshot is always fully enriched, or it is
  not updated at all.
- **Missing snapshot at dispatch.** If a `[visual_fidelity]` project has no committed snapshot,
  `visual-fidelity-check`'s existing fail-closed behavior applies (it surfaces the gap and does
  not pass) — unchanged.
- **Stale snapshot.** Not auto-detected at dispatch (no per-dispatch Figma call, by design).
  Mitigated by the §4 trigger and the `--check` freshness command. Accepted residual risk.

## Testing

- `crew figma-snapshot` REST-only path: existing `emit` / `client` tests stay; `runFigmaSnapshot`
  test updates to drop the enrichment-call assertion.
- `--check`: new tests — fresh (versions match) and stale (versions differ), using the injectable
  REST client seam.
- `figmaFileVersion` is recorded in `index.json`: covered by an `emit` test.
- Deleted code's tests (`figma-snapshot-step.test.ts`, `plugin-api-enrichment.test.ts`,
  `enrichment-prompt.test.ts`) are removed; `run.test.ts` drops the pre-dispatch assertion.
- The `figma-snapshot-refresh` skill is verified by authoring it interactively and running it
  once end-to-end to produce the first committed snapshot (the skill is markdown + a JS asset;
  its "test" is a successful real regeneration).

## Out of scope / follow-ups

- **CREW-152 re-plan.** Its Task 4.1 ("consume the pre-dispatch snapshot") premise is gone; it
  now means "the committed snapshot is current." CREW-152 needs re-scoping — a follow-up, not
  this spec.
- **CREW-172** is already merged; its figma-subprocess fix is mooted by §1 (that code is
  deleted). Nothing to undo — the `spawn.ts` half is still in use.
- **Automated staleness enforcement** (e.g. blocking a dispatch on a stale snapshot) — not
  built; `--check` is opt-in. Revisit if the trigger proves insufficient in practice.

## Execution shape

Two units of work:

- **Autonomous (`crew run`):** §1, §2, §6, §7's `.agents/dispatch.md` + `visual-fidelity-setup.md`
  edits, `.gitignore` (§5) — all CLI/config/doc code, dispatchable.
- **Interactive (in-session):** §3 (authoring the `figma-snapshot-refresh` skill — skill files
  under `.claude/skills/` cannot be a `crew run`), §4's `.agents/design-system.md` rule, and the
  first real regeneration that produces the committed snapshot.

Detailed sequencing is for the implementation plan.
