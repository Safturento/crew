# CLAUDE.md

Conventions for agents working on `crew` itself. The full design is in [`docs/plans/architecture.md`](./docs/plans/architecture.md); read that first before any non-trivial change.

## Repo layout

npm workspaces monorepo. Each package lives under `packages/`:

```
crew/
├── packages/
│   ├── cli/         # the `crew` command users invoke
│   ├── daemon/      # long-running state-tracking process
│   ├── dashboard/   # React + Vite web UI
│   └── shared/      # types, transcript parsing, project config, jira/github clients
└── docs/
```

Install dependencies into the specific workspace that uses them (`npm install <pkg> --workspace=crew-cli`), not the root. The `--workspace` flag takes the package's `name` (e.g. `crew-cli`, `crew-daemon`), not the directory name. Root `package.json` should stay free of runtime dependencies — it's just workspace orchestration and root-level lint/format/test wrappers.

## Package versions

Always install the latest stable version of any npm package — use `npm install <pkg>@latest` directly without checking the dist-tag first. This applies to both `dependencies` and `devDependencies`. Always install/update any relevant `@types` packages as devDependencies.

## Code cleanliness

Before reporting any task as complete, run `npm run lint` and `npm run format` and resolve everything they surface — the working tree should be free of ESLint warnings/errors and Prettier diffs when you hand off.

- Treat warnings as errors. A clean baseline is the only useful baseline.
- Fix the underlying issue rather than silencing it. Don't reach for `eslint-disable`, `// @ts-ignore`/`@ts-expect-error`, `any`, or non-null assertions. If a lint rule is firing, address it.
- The same applies to type errors from `npm run typecheck` — fix the types, don't paper over them.

## Conventions inherited from the Recipes-App scripts era

These came from real pain on the precursor project. Worth preserving:

- **LF line endings everywhere.** `.gitattributes` already enforces `eol=lf`. Don't introduce CRLF text files; if a tool generates them, fix the tool.
- **`tsbuildinfo` files are gitignored, never committed.** Already in `.gitignore`.
- **Refuse to clobber a file we didn't generate.** When a script writes to a file that might also be hand-edited (e.g., `.env`, `settings.json`), tag the generated version with a `# generated by crew` header and refuse to overwrite if the header is missing.
- **TOML over JSON for human-edited config.** Project configs, secrets manifests, anything a human will touch directly. Use TOML. Reserve JSON for machine-generated files.
- **Per-worktree docker isolation.** When generating a docker `.env`, hash the worktree basename to derive non-default ports so multiple worktrees coexist without collision.
- **Bin scripts need an explicit executable bit in the index.** The repo has `core.filemode = false`, so `chmod +x` alone won't propagate to commits. After `chmod +x`, run `git update-index --add --chmod=+x <path>` so the file lands as `100755`.

## Architecture rules

These flow from the design plan:

- **The CLI never embeds business logic that belongs in `shared/`.** Subcommands should be thin wrappers: parse args, call shared, render output.
- **The daemon never reads from disk for things the CLI can pass.** State queries go through the daemon's API; the CLI passes the question.
- **`shared/` has no CLI / daemon / dashboard imports.** It's the leaf of the dependency graph.
- **No business logic in the dashboard.** It's a view over the daemon's API.
- **Per-project config is the only place project-specific knowledge lives.** Don't hardcode "Recipes-App" anywhere; everything's parameterised on the loaded project config.

## Testing

- Vitest for unit tests on `shared/`, `cli/`, `daemon/`.
- React Testing Library for `dashboard/`.
- Tests live alongside the file they exercise: `foo.ts` + `foo.test.ts`.
- For the daemon's filesystem watching, use `tmpdir`-based fixtures rather than mocking — the integration is small and the failure mode (a missed event) is easy to mask with a too-clever mock.

## Design plans

Notable design decisions live as markdown docs in `docs/plans/`. One file per topic, named after the decision. Update or create a plan doc whenever a long conversation produces something a future reader (or future me) shouldn't have to re-derive.

The design doc structure mirrors what worked in the Recipes-App:

1. Context — the generic problem
2. Options considered — with trade-offs
3. Recommendation by context
4. Chosen approach — for *this* project
5. Implementation outline
6. Verification
7. Non-goals
8. Forward path

## Ticket context (`docs/tickets/`)

One file per Jira ticket, named by the key (e.g. `docs/tickets/CREW-3.md`). Working scratchpads — decisions made mid-implementation, files touched, open questions, dead ends. Not a duplicate of Jira.

When a ticket ships, durable knowledge graduates: design-level decisions go to `docs/plans/`, change rationale goes into the commit message / PR description. The ticket file itself can be deleted or pruned after merge.

Don't create a ticket file for one-shot work that finishes in a session. The signal is "would we forget this if we paused for a week?" — if no, skip it.
