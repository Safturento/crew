# Testing

Crew has three test surfaces. Each has its own home, runner, and trigger rule.

| Surface           | Location                                 | Runner          | Trigger to run                                 |
| ----------------- | ---------------------------------------- | --------------- | ---------------------------------------------- |
| Unit              | `packages/*/src/**/*.test.ts`            | Vitest          | Always part of `npm run test:run`              |
| API smoke (Bruno) | `bruno/endpoints/`, `bruno/flows/`       | `@usebruno/cli` | `npm run bruno:smoke` (needs `CREW_BRUNO_ENV`) |
| Dashboard e2e     | `packages/dashboard/tests/e2e/*.spec.ts` | Playwright      | `npm run test:e2e`                             |

Unit tests live alongside source (`foo.ts` + `foo.test.ts`). E2e tests live in their own `tests/e2e/` tree because they need the dashboard built and the worktree's docker stack running.

## Bruno collection (`bruno/`)

Smokes the daemon's HTTP API.

- `bruno/bruno.json` — collection root marker.
- `bruno/endpoints/<group>/<verb>-<name>.bru` — one file per (route, verb) pair. Reference card for that endpoint.
- `bruno/flows/<flow>.bru` — chained user journeys. Today only `main-smoke.bru`, exercised by `npm run bruno:smoke`.
- `bruno/environments/` — **gitignored**. Per-worktree env files are generated by the bruno-smoke writer (`packages/cli/src/lib/bruno-smoke/`) at agent dispatch time. For local dev, hand-author one (e.g. `bruno/environments/local.bru` with `vars { baseUrl: http://localhost:7773 }`) and run `CREW_BRUNO_ENV=local npm run bruno:smoke`.

### Same-commit rule

Whenever you add, rename, or change the request/response shape of an HTTP route in `packages/daemon/`, update the matching `bruno/endpoints/<group>/<verb>-<name>.bru` (and any `flows/*.bru` that exercises it) in the **same commit**. Coverage drifts silently the moment a route changes without its `.bru`.

The `bruno-collection-maintenance` skill — a crew-owned skill committed at `<repo>/.claude/skills/bruno-collection-maintenance/` and injected into every dispatched worktree — is the authority on naming, the `vars:post-response` chaining pattern, and the full list of triggering events. Don't duplicate that content here; Claude Code discovers the injected skill natively for any agent dispatched into this repo via `crew run`.

## Dashboard e2e (Playwright)

`packages/dashboard/playwright.config.ts` drives the suite. Specs live in `packages/dashboard/tests/e2e/*.spec.ts`. Run with:

```bash
npm run test:e2e              # alias for `playwright test` in the dashboard workspace
```

The runner has no `webServer` block — it expects the worktree's docker stack to already be up. `baseURL` resolves in this order:

1. `PLAYWRIGHT_BASE_URL` env var, if set.
2. `APP_URL=` line in the worktree's root `.env` (materialized from `env.toml` by `crew env init` / `crew env refresh`).

If neither is present the config throws with a pointer to those commands — that's the right failure mode; do not paper over it.

E2e tests assert **shape, not specific fixture names**. The daemon's seed pins project names (`crew`, `recipes`) and agent keys today, but the dashboard contract is "group agents by project," not "render these two strings." Selectors that read like `getByRole('button', { name: /^Toggle / })` survive future fixture renames; selectors that hardcode `"crew"` do not.

## Daemon fixture seeding (`CREW_SEED_FIXTURES`)

Worktree DBs come up empty by default (anonymous volume per stack). The daemon's entrypoint (`packages/daemon/src/serve.ts`) runs `packages/daemon/seeds/dev.ts` after migrations **only when** `CREW_SEED_FIXTURES=1`.

Key behavior:

- **Auto-injected for non-canonical worktrees only.** `packages/cli/src/lib/env-spec/materialize.ts` sets `CREW_SEED_FIXTURES=1` in every worktree `.env` whose `isCanonical=false`. Canonical worktrees intentionally skip the seed — their state is the user's real registered work, not a sample.
- **Idempotent.** `seedFixtures()` gates on `agents` already having rows; running twice is a no-op, not a duplicate-key crash.
- **Project TOMLs are seeded too.** `serve.ts` writes `crew.toml` and `recipes.toml` into the daemon's `configDir` alongside the DB rows. Without those files, `ProjectsService` filters every fixture agent off the `/api/projects` response and the dashboard renders an empty grid.

If your local stack has no fixtures and you expected some, check: are you in the canonical worktree (which skips the seed by design), or is `CREW_SEED_FIXTURES=1` missing from `.env`?

## Daemon unit-test harness (`packages/daemon/vitest.config.ts`)

The daemon package carries its own `vitest.config.ts` (closest-config wins over the repo-root one) so it can register a `setupFiles` entry, `src/test/setup.ts`. That setup file pins both `CREW_STARTUP_EVENTS_DIR` and `CREW_STATE_EVENTS_DIR` (CREW-254) at fresh empty temp dirs for the whole package's test run.

Why it exists: any test that builds the full app (`buildApp`) triggers the `onReady` hook's two chokidar watchers — one on the startup-event dir, one on the state-event dir. Unisolated, those default to the developer's real `~/.crew/startup` and `~/.crew/state-events`, and chokidar's initial scan (`ignoreInitial:false`) replays every historical `<key>.jsonl` through `IngestService` — a burst of synchronous SQLite writes on the shared db that starves later `app.inject` calls and trips the 5s test timeout. The setup file makes both scans always a no-op, so individual tests don't each have to isolate the env vars themselves.

Each watcher reads its dir from config (`config.startupEventsDir` / `config.stateEventsDir`), not `process.env` (CREW-236): the matching `CREW_*_EVENTS_DIR` field defaults to `process.env.<VAR> ?? ~/.crew/<dir>`, so the `src/test/setup.ts` env pins still flow through for tests that build config from a partial env object. A test that wants its own dir overrides it explicitly via `parseDaemonConfig({ CREW_STARTUP_EVENTS_DIR: ... })` (see `routes/events.test.ts`) rather than juggling `process.env`.

## Sandboxed vs un-sandboxed test runs

`crew run` dispatches agents inside a Bash sandbox that has its own loopback, isolated from the host's. Direct `curl` / `wget` / Node `fetch` calls from the agent's shell to `http://localhost:<port>` return `ECONNREFUSED` — that is **not** evidence the stack is down.

`<repo>/.claude/settings.json`'s `excludedCommands` whitelists the only commands that need host-loopback reachability:

```json
"excludedCommands": [
  "npm run bruno:smoke*",
  "npm run test:e2e*",
  "docker compose*"
]
```

The match is a glob with leading-substring semantics — `command*` accepts zero-or-more trailing chars (`--workspace=...`, redirects, etc.) but **wrappers defeat the match**:

- ✅ `npm run test:e2e`, `npm run test:e2e --workspace=crew-dashboard`, `npm run bruno:smoke 2>&1 | tail`
- ❌ `cd packages/dashboard && npm run test:e2e`, `npm --prefix packages/dashboard run test:e2e`, `sh -c "npm run test:e2e"`

A failing wrapped command produces `ECONNREFUSED` while the same flow works fine through MCP — that's the signature of a wrapper-defeated match. Run the bare command.

See [`local-dev.md`](local-dev.md) for the full sandbox model and `${VAR}` env-resolution rules.

## Verification gates

When claiming work done, run the full cleanliness sweep before opening the PR:

```bash
npm run lint && npm run format:check && npm run typecheck && npm run test:run
```

For changes that touch HTTP routes or UI flows, add the relevant smoke run:

```bash
CREW_BRUNO_ENV=local npm run bruno:smoke   # API
npm run test:e2e                            # UI
```
